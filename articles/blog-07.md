今天了解一个新的名字——skills，在今天之前我也只是属于仅仅听过这个词，它究竟是什么，怎么创建skills，如何使用它我一概不知。今天又是从零开始学习的一天，希望今天你也能有所收获。

## 理论：了解什么是skills
- 查找的资料解释：一个技能就是一个文件夹，里面放一份SKILL.md文件，写清楚"这类任务应该怎么做"，还可以附带参考资料、脚本等。比如做PPT、做表格、做PDF、管理日历、发邮件，各有各的技能，Codex 遇到相关任务时就会照着对应说明书干活。它的好处是"按需加载"：平时Codex只看到每个技能的名字和一句话简介，不会占用太多上下文；只有当你的任务真的匹配某个技能时，它才会把完整的说明书读进来，这样既准确又不浪费。你不需要做任何特殊操作——直接说需求就行，Codex 会根据任务自动判断该用哪个技能。
- 我理解的skil：它是一个能约束AI发散的框架，AI是会思考的，它的发散是很广阔的，那么如何才能更高效的让AI做出符合我们要求的产品呢？那就是创建你的skills，它无论做什么产品都会按照固定的大概流程与要求思考，这样的它做出来的就不是一个dome，而是一个project。很显然它能节省你的上下文和token。

## 准备：让AI制作一个我的skills
### 之前聊过，一个产品从0到1的话需要一个团队的合作，其中包括需求方、产品经理、程序员、运营、测试。那我们就创建一个skills，让AI每次生产产品的时候都要模拟一个团队讨论三遍以上且生成产品文档和技术文档之后才生产。
**eg：我希望做一个skills名字叫Quick start project，后续我做的所有项目，都要遵循这个skills，在项目生成中一定要有需求方，产品经理，程序员。如果项目较为复杂的话还需要加上运营与测试，用专业知识来支持我的产品，严格要求产品的产出一定要经过这些角色三轮的对话，接下来的产品一定遵循他们讨论生成的产品文档与技术文档，并且能随时迭代更新。我想要一个强大的skills来支持一下我的要求。我们先来讨论一下。**
### 你不需要做任何特殊操作——直接说需求就行，它会给你选择：
**在动手创建之前，有三个问题想先跟你确认：
问题 1：角色扮演方式。 你希望我在对话里直接同时扮演 PM/程序员/运营/测试，你以需求方身份参与，我们像开会一样对话推进？还是你想在某些环节亲自指定角色发言？（我推荐前者，效率最高）
问题 2：三轮对话的定义。 我上面提的「需求澄清 → 方案评审 → 定稿验收」这个三轮结构你认可吗？还是你心里有别的三轮划分，比如「需求方和 PM 聊三轮，再 PM 和程序员聊三轮」？
问题 3：复杂项目的判定。 我打算用清单自动判定：是否多用户、是否涉及支付/数据存储、功能是否超过约5？个、是否要上线运营……满足任一条件就自动加上运营和测试。这个判定逻辑你觉得合理，还是希望默认所有项目都带齐五个角色？**

# Quick Start Project（快速启动项目）

## 核心规则

- 用户永远是需求方（Stakeholder）；Codex 在对话中扮演其余角色，每次发言必须用「角色：内容」格式标注。
- 简单项目至少包含：需求方、产品经理、程序员。复杂项目额外增加：运营、测试。
- 任何项目必须先完成三轮跨角色对话（需求澄清 → 方案评审 → 定稿与验收），并取得需求方明确确认后，才能进入开发。
- 开发必须严格遵循三轮讨论产出的产品文档与技术文档；发现文档问题时先走变更流程，不得自行偏离。
- 项目可随时迭代：迭代走轻量变更协议，文档与代码必须同步更新。

## 启动流程

### 1. 项目初始化

收到新项目请求后：

1. 向需求方收集最少启动信息：项目名称、一句话目标、目标用户、核心功能（可多轮追问，但不要一次性抛过多问题）。
2. 按 [checklist.md](references/checklist.md) 判定复杂度，确定角色阵容：
   - 简单项目：需求方 + 产品经理 + 程序员
   - 复杂项目：需求方 + 产品经理 + 程序员 + 运营 + 测试
3. 创建项目目录与 `docs/` 结构：
   - `docs/prd.md`（产品需求文档）
   - `docs/technical-design.md`（技术设计文档）
   - `docs/meetings/round-1.md`、`round-2.md`、`round-3.md`
   - `docs/changelog.md`（变更日志）

### 2. 三轮强制对话

每一轮都必须是真实的跨角色对话（相互提问、质疑、回应），并同步写入对应会议纪要。模板见 [meeting-template.md](references/meeting-template.md)。

- **第 1 轮 · 需求澄清**：需求方说明目标 → 产品经理追问（目标用户、核心场景、成功标准）→ 程序员做可行性初判与风险提示 → 产出 PRD v0.1 与技术方案 v0.1。
- **第 2 轮 · 方案评审**：产品经理陈述产品方案与优先级 → 程序员陈述技术选型与架构 → 运营（复杂项目）评审上线节奏与数据指标 → 测试（复杂项目）评审可测性与测试策略 → 文档更新至 v0.2，列出开放问题。
- **第 3 轮 · 定稿与验收**：逐条核对验收标准、风险清单与里程碑 → 冻结文档为 v1.0 → 请需求方（用户）明确确认「同意按此文档开发」→ 确认后方可进入实现。

### 3. 文档驱动开发

- 实现严格对照 `docs/prd.md` 与 `docs/technical-design.md`，每个功能与验收标准一一对应。
- 开发中若发现文档遗漏或矛盾：按 [iteration.md](references/iteration.md) 发起变更请求，先改文档再改代码。

### 4. 完成门槛

交付前必须逐项通过 [checklist.md](references/checklist.md) 中的完成清单，核心包括：

- 三份会议纪要齐全，每轮至少两个角色有实质发言。
- PRD 与技术文档存在冻结版本（v1.0 或更高）。
- 验收标准全部通过；复杂项目还需测试计划与执行记录。
- 变更日志已记录全部迭代。
- 向需求方提交交付说明，未获确认不得宣称完成。

## 迭代协议

用户提出「迭代」「更新」「修改」时：

1. 记录变更请求：提出人、变更内容、原因。
2. 产品经理评估影响 → 程序员给出方案与工作量 → 测试（如有）确认回归范围。
3. 更新文档并记入 `docs/changelog.md`；版本规则：小改 v1.1，新增功能 v1.x，破坏性变更升 v2.0。
4. 按更新后的文档实现并验证，向需求方汇报。
5. 简单变更可合并为一轮对话，但文档更新不可省略。

详细协议见 [iteration.md](references/iteration.md)。
